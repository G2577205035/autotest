# 模型评测模块技术方案

> 文档版本：V1.3
> 编制日期：2026-09-02
> 当前状态：工作日 1～2 已完成，基础评测 MVP、平台页面闭环与 EvalScope 1.11.1 复验通过；第一台真实模型联调外部待验
> 适用项目：烈马自动化测试平台

## 1. 建设目标

在现有“模型配置中心”之外建设独立的“模型评测中心”，用于评估私有化部署大模型的能力质量、翻译质量、服务性能、并发与负载、鲁棒性、报告写作和情报生产能力，并形成可复现、可比较、可追溯的 DOCX/PDF 评测报告。

模块采用以下产品原则：

1. 平台提供开箱即用的内置标准测试集，没有业务素材也能完成基础评测。
2. 支持用户按项目上传、编辑和版本化自己的业务测试素材。
3. 测试集版本、模型参数和运行环境形成不可变快照，保证结果可以复验。
4. “能力质量”和“服务性能”分别评分，不使用单一总分掩盖模型差异。
5. 自动规则优先，裁判模型和人工复核作为进阶评分手段。
6. 模型密钥不进入任务快照、测试日志、评测产物和报告。
7. 负载测试默认设置安全护栏，不自动执行 GPU 烧卡，也不自动停止业务服务。
8. 复用平台现有 MySQL/SQLite、MinIO/本地 Artifact Storage、Redis 信号队列、外部 Worker、RBAC、审计和报告能力，继续保持模块化单体，不推倒重写。
9. 标准能力、标准数据集和推理性能优先复用成熟的 EvalScope 引擎，平台集中建设项目化编排、业务专项和企业交付能力。

## 2. 范围与非目标

### 2.1 本模块范围

- 模型服务协议与能力探测。
- Token、上下文长度和输出长度遵循测试。
- 指令遵循、结构化输出和基础能力测试。
- 并发、吞吐、时延、容量拐点、突发和持续负载测试。
- 鲁棒性、重复一致性和基础安全测试。
- 中英双向翻译及可扩展多语种翻译测试。
- 报告写作和情报生产专项测试。
- 内置测试集、用户测试集、版本、导入和复制。
- 自动评分、裁判模型评分、人工复核入口。
- 运行监控、结果分析、同版本对比和 DOCX/PDF 报告。

### 2.2 首版非目标

- 不自动下载来源不明的模型权重或 Tokenizer 代码。
- 不修改被测模型服务、推理框架、驱动、CUDA 或服务器配置。
- 不把推理负载测试等同于 `gpu-burn` 等硬件满载压测。
- 不承诺一次评测覆盖所有行业知识或所有语种。
- 不用被测模型给自己生成正式质量分；确需自评时只展示为低置信参考项。
- 首版不直接嵌入完整 OpenCompass 调度体系；确需使用时通过 EvalScope 的可选后端接入并单独安装依赖。
- 首版不实现 RAG 检索链和 Agent 工具链评测；模型具备这些能力时作为后续可选扩展。

## 3. 与现有平台的集成边界

### 3.1 可直接复用的能力

| 现有能力 | 模型评测中的用途 |
| --- | --- |
| 模型配置中心 | 选择被测模型和裁判模型，安全解析调用凭据 |
| Platform Store | 保存测试集索引、版本、运行、结果摘要和审计字段 |
| Artifact Storage | 保存原始输入输出、明细指标、图表和报告，生产环境落 MinIO |
| Task Signal Queue | Redis 只发送轻量唤醒信号，数据库作为最终事实源 |
| 独立 Worker | 执行评测、评分和报告生成，不阻塞 Web 请求 |
| 服务器资产与会话 | 可选关联推理服务器，采集 CPU、内存和 GPU 资源指标 |
| 报告基础设施 | 生成 DOCX/PDF、图表和可下载产物 |
| 用户、项目、RBAC、审计 | 项目隔离、操作授权、测试集和结果访问控制 |

### 3.2 需要新增或扩展的能力

当前模型调用只适合普通非流式文本调用。模型评测新增统一 `EvaluationBackend` 边界，默认由两个后端组合完成：

- `EvalScopeBackend`：标准公开 Benchmark、标准裁判、逐请求性能采集、并发/RPS/长上下文和 WMT 翻译评测。
- `NativeBusinessBackend`：平台内置合成用例、鲁棒扰动分组、术语/实体/格式规则、报告写作、情报生产和用户自定义材料。

`EvaluationModelClient` 保留为模型协议探测、快速烟雾测试和原生业务后端的调用适配器，不再重复实现 EvalScope 已成熟覆盖的全部标准评测和压测逻辑。它需要支持：

- OpenAI 兼容 Chat Completions 接口。
- 无鉴权、Bearer Token 和自定义请求头三种鉴权方式。
- 流式与非流式调用。
- 首 Token 时间、分片时间和流式异常采集。
- `usage` Token 用量读取、Tokenizer 计数适配和估算降级。
- 超时、取消、重试、连接错误、HTTP 状态和结束原因归一化。
- 每次请求的模型参数和协议能力快照。

模型配置建议增加以下非敏感字段：

| 字段 | 说明 |
| --- | --- |
| `protocol_type` | 首版支持 `openai_chat`，后续扩展其他协议 |
| `auth_type` | `none`、`bearer`、`custom_header` |
| `auth_header_name` | 自定义鉴权头名称；值仍进入加密凭据 |
| `supports_stream` | 是否支持流式返回 |
| `context_window` | 声明的最大上下文长度 |
| `max_output_tokens` | 建议最大输出长度 |
| `tokenizer_mode` | `api_usage`、`local_tokenizer`、`estimate` |
| `tokenizer_reference` | 可选的已安装本地 Tokenizer 标识或受控路径 |
| `engine_name/version` | vLLM、SGLang、TGI、Ollama 等推理引擎信息 |
| `model_version/quantization` | 模型版本和量化方式 |

凭据字段继续复用现有加密机制，列表和评测快照永不返回明文或密文。

### 3.3 EvalScope 集成决策

EvalScope 是模型评测的底层执行引擎之一，不替代烈马平台本身。边界如下：

| 能力 | EvalScope 负责 | 烈马平台负责 |
| --- | --- | --- |
| 标准能力评测 | MMLU、C-Eval、CMMLU、GSM8K、IFEval 等 Benchmark 适配、推理和标准指标 | 测试套餐、项目权限、版本快照、运行编排和统一结果解释 |
| 推理性能 | TTFT、TPOT、时延、Token 吞吐、固定并发、固定/开放环 RPS、预热和性能产物 | 容量阶梯策略、同端点互斥、安全停止、服务器资源关联和企业结论 |
| Token/长上下文 | Tokenizer、随机定长输入、LongAlpaca/自定义数据和逐请求性能 | Token 来源可信度、上下文业务用例和验收口径 |
| 翻译 | WMT2024++、BLEU、BERTScore、COMET 等标准评测 | 中译英业务集、术语/实体/数字/格式规则、用户术语表和人工复核 |
| 鲁棒性 | 指令遵循、幻觉、长上下文等标准 Benchmark | 基准/扰动成组生成、保持值、最差值和业务噪声 |
| 报告/情报 | 可复用自定义 Benchmark、Sample、Metric 和 Judge 扩展接口 | 材料包、黄金事实、禁编项、业务 Rubric、来源追溯和专项报告 |
| 可视化 | 不复用其独立 WebUI | 保持烈马统一页面、RBAC、审计、项目隔离和 DOCX/PDF 报告 |

首选集成方式是“固定版本的隔离运行时 + 适配器子进程/独立 Evaluation Worker”，不在 FastAPI Web 进程内直接加载整套依赖，也不把 EvalScope WebUI 暴露给用户。原因是：

- EvalScope 的服务接口适合远程调用，但官方文档中的评测/压测请求仍是长时间同步请求；烈马已有持久化队列、停止、恢复和事件流。
- EvalScope 含多组可选依赖，隔离运行可降低与现有 FastAPI、报告和离线镜像依赖冲突的风险。
- 子进程可由平台记录 PID/租约并协作停止，产物写入单次运行目录后再由结果映射器导入。
- 凭据通过仅对子进程可见的临时环境或受限临时配置传入，完成即清理，不进入命令行、日志和产物。
- 不启动 EvalScope 默认 9000 端口，不引入第二套用户界面，也不影响 PyCharm 使用现有 8080 启动平台。

阶段 0 必须先完成固定版本兼容性 PoC，再决定同一 Worker 内的隔离子进程是否足够；正式环境依赖较重时直接形成独立 Evaluation Worker 镜像。平台依赖的是自有 `EvaluationBackend` 契约，不直接依赖 EvalScope 内部非公开实现。

## 4. 总体架构

```text
模型评测页面
    │
    ├── 测试集管理 ────────> Platform Store ──> 测试集/版本/用例索引
    │                              │
    │                              └──────────> Artifact Store ──> 用户材料与大文件
    │
    └── 提交评测 ──────────> Evaluation API ──> 持久化评测运行
                                      │
                                      └──────> Redis/Local Signal Queue
                                                     │
                                                     v
                                            Model Evaluation Worker
                                             │       │
                                             │       └────────── 可选服务器指标采集
                                             v
                                      EvaluationBackend Adapter
                                        │                 │
                                        │                 └── Native Business Backend
                                        v
                              隔离 EvalScope Runtime（eval/perf/WMT）
                                        │
                                        └────────────────> 被测模型/裁判模型服务
                                                     │
                              Platform Store <───────┤ 摘要、状态、索引
                              Artifact Store <───────┤ JSONL/CSV/图表/快照
                              Report Builder <───────┘ DOCX/PDF
```

## 5. 评测维度与指标

### 5.1 Token 与上下文能力

| 指标 | 计算口径 |
| --- | --- |
| 输入/输出/总 Token | 优先读取 API `usage`，其次使用匹配的本地 Tokenizer，否则标记为估算 |
| 输出长度遵循率 | 实际输出 Token 是否落在目标区间 |
| 截断率 | `finish_reason=length` 或输出非预期中断的用例占比 |
| 空响应率 | 成功 HTTP 响应但无有效正文的比例 |
| 上下文召回率 | 长上下文中指定关键事实的命中比例 |
| 长度退化曲线 | 输入长度增加时正确率、TTFT、吞吐和错误率的变化 |
| Token 膨胀率 | 输出 Token / 输入 Token，用于翻译、摘要和报告任务分析 |

Token 来源必须随结果展示：`api_usage`、`local_tokenizer` 或 `estimated`。估算值可以用于趋势观察，但不进入精确 Token 验收结论。

### 5.2 基础能力与指令遵循

- 指令完成率、事实准确率、关键信息召回率。
- 摘要覆盖率、信息抽取准确率、分类准确率。
- JSON 合法率、Schema 字段完整率、类型正确率。
- 字数、语种、格式、禁止项和固定表达遵循率。
- 多轮上下文一致性和前文信息保持率。
- 中英文及混合语言处理能力。

首版以内置规则可稳定评分的任务为主，不把开放式推理题的裁判分当成唯一依据。

### 5.3 单请求性能

| 指标 | 说明 |
| --- | --- |
| TTFT | 请求发出到收到第一个非空内容分片的时间 |
| TPOT | 从首 Token 到完成的时间 / 后续输出 Token 数 |
| ITL | 相邻有效输出分片或 Token 的时间间隔，支持时输出 |
| E2E Latency | 请求到完整响应的总时间 |
| Output Token Throughput | 单请求输出 Token / 生成阶段时间 |
| 冷/热启动差异 | 首次调用与预热后调用的时延差 |

所有时间使用单调时钟采集；报告至少输出平均值、P50、P90、P95、P99、最小值和最大值。

### 5.4 并发、负载与容量

- 固定并发：并发数阶梯增长，保持每个并发位持续有请求。
- 固定到达率：按目标 RPS 发起请求，观察排队和超时。
- 突发测试：在短时间注入高于稳态的请求量，观察退化与恢复。
- 持续测试：在安全负载下持续运行，观察吞吐和资源是否随时间恶化。
- 输入/输出长度矩阵：短输入短输出、短输入长输出、长输入短输出、长输入长输出。

核心指标包括：

- 请求吞吐 RPS、输出 Token/s、总 Token/s。
- 成功率、超时率、取消率、429、4xx、5xx、连接错误率。
- TTFT 和 E2E 的 P50/P95/P99。
- 排队时间；服务不可提供时明确标记不可采集，而不是填 0。
- 最大稳定并发、最大稳定 RPS、容量拐点和突发恢复时间。
- 冷启动、预热后和持续运行阶段的差异。

“最大稳定容量”不是单看请求是否返回。默认要求一个测量窗口内同时满足：成功率不低于阈值、P95 不超过基线倍数或绝对上限、错误率不超过阈值、服务器安全阈值未触发。阈值保存在运行快照中，可按项目调整。

### 5.5 资源与可靠性

关联服务器会话时采集：

- GPU 使用率、显存使用量/占比、温度、功耗、频率和逐卡负载均衡。
- CPU 使用率、可信 CPU 温度、内存、磁盘和网络指标。
- 可取得时的 KV Cache 使用率、排队长度和推理引擎指标。
- 每千输出 Token 的 GPU 时间或能耗参考值。

可靠性用例覆盖非法参数、超长输入、请求取消、重复请求、连接重置、超时、服务重启后的恢复和长时间运行后的内存回收。未绑定服务器时仍可完成接口侧评测，只把资源指标标记为“未采集”。

### 5.6 鲁棒性

内置扰动类型包括：

- 同义改写、语序变化、主动/被动表达变化。
- 错别字、漏字、重复字、OCR 噪声、乱码和异常空白。
- 无关长文本、字段顺序变化、大小写和标点变化。
- 中英混排、语言切换和不同表达风格。
- 冲突指令、提示词注入、虚假前提和证据不足场景。
- 相同请求多次运行的一致性与重试稳定性。

每个鲁棒用例由一个基准用例和多个扰动变体组成。建议使用：

```text
单变体保持值 = min(扰动得分 / 基准得分, 1) × 100
平均鲁棒值   = 所有有效变体保持值的平均数
最差鲁棒值   = 所有有效变体保持值的最小值
```

只有基准得分达到配置阈值时才计算保持值；如果模型连原始问题都不能完成，鲁棒值标记为 `N/A`，避免低基线产生虚假的高鲁棒分。

### 5.7 翻译能力

翻译作为独立一级维度，首版内置中译英和英译中，数据结构允许扩展其他语种。

评测内容包括：

- 通用短句、新闻通知、技术说明、报告材料和情报材料。
- 长文档、跨段落指代和术语一致性。
- 人名、机构、地点、时间、金额、数字和计量单位。
- Markdown、表格、JSON、HTML、编号、链接和占位符保持。
- 错别字、OCR 噪声、断句错误、中英混排和口语表达。
- 指定术语、专名、文体、目标读者和不得翻译的保护片段。

翻译用例字段至少包含：

- 原文、源语言、目标语言。
- 一份或多份参考译文。
- 术语表、专名表、保护片段和可接受译法。
- 必须保留的数字、实体、单位和格式。
- 文体要求、禁止错误和评分权重。

默认翻译质量权重：

| 维度 | 权重 |
| --- | ---: |
| 忠实度与完整性 | 35% |
| 术语与实体准确性 | 20% |
| 流畅度 | 15% |
| 格式和数字保持 | 10% |
| 上下文一致性 | 10% |
| 鲁棒性 | 10% |

规则评分负责数字、实体、术语、格式和漏译检查；chrF/BLEU 仅作为低权重参考；语义质量由可选语义评分器、独立裁判模型或人工复核完成。不得因为译法与唯一参考答案字面不同就直接判错。

翻译性能同时进入服务性能结果，展示翻译 TTFT、页/千字耗时、Token 吞吐、并发成功率和译文 Token 膨胀率。

### 5.8 报告写作能力

内置场景包括事件调查、风险分析、专项总结、周报/月报、数据统计分析、多材料综合研判和舆情分析。主要指标为：

- 必须事实、数字、人物、时间和结论覆盖率。
- 无依据事实、数字和来源的虚构比例。
- 章节结构、模板和篇幅遵循率。
- 来源可追溯性、引用准确性和事实一致性。
- 内容重复率、逻辑连贯性、语言规范性和可读性。
- 明确区分事实、推断、风险和建议的能力。

每个材料包包含原始材料、任务说明、必需事实、禁止虚构项、期望结构、评分 Rubric 和可选参考报告。

### 5.9 情报生产能力

内置场景包括情报快报、多来源汇总、实体与事件提取、时间线重建、关系整理、矛盾识别、信源分析、风险预警和趋势研判。主要指标为：

- 实体、事件和关系准确率。
- 关键事实召回率和时间线准确率。
- 多来源去重、合并和来源映射准确性。
- 矛盾信息识别率和信源可靠性表达。
- 事实与推测区分能力、不确定性表达能力。
- 关键线索召回率、证据支撑率和建议可执行性。
- 虚构情报、虚构来源和无依据结论比例。

内置素材全部使用虚构或可公开数据，不包含真实公司、案件和敏感情报。

### 5.10 条件扩展维度

当模型实际承载相应能力时再启用：

- RAG：Recall@K、上下文命中、引用准确率、Groundedness 和无证据回答率。
- Agent/工具调用：工具选择、参数正确率、调用成功率、步骤效率和错误恢复。
- 多模态：OCR、图表理解、图文一致性和视觉问答。

这些维度不进入首版验收，避免扩大首期范围。

## 6. 内置测试集规划

### 6.1 测试集形态

测试集分为三类来源：

- `platform_builtin`：烈马自有合成/公开可分发素材，随平台离线发布。
- `evalscope_catalog`：EvalScope 标准 Benchmark 目录；数据内容需要按许可证下载、审批并固化到本地缓存。
- `project_custom`：用户在当前项目创建或导入的业务素材。

内置和标准测试集具备以下属性：

- `source=builtin`，只读、不可原地修改。
- 每次平台发布使用明确版本号和内容 SHA-256。
- 用户需要调整时执行“复制为项目测试集”。
- 内置答案、评分规则和裁判提示与用例共同版本化。
- 同一运行只引用不可变的测试集版本，不引用可变草稿。
- EvalScope 目录项额外记录 EvalScope 版本、Benchmark 名称、上游数据集 ID、子集、数据版本、许可证和本地内容哈希。

第三方 Benchmark 的“平台内置”指页面内置可选择的标准目录，不代表平台可以不经许可证核验直接重新分发其完整数据。正式离线环境由管理员在有网构建区预下载、核验许可证和哈希后导入，本地运行强制使用本地数据源。

### 6.2 首版内置规模

| 测试包 | 首版目标 | 说明 |
| --- | ---: | --- |
| 基础能力与结构化输出 | 不少于 80 条 | 指令、抽取、分类、摘要、JSON、格式 |
| Token/上下文边界 | 不少于 30 条 | 输入/输出长度矩阵和上下文召回 |
| 并发随机提示词池 | 不少于 150 条 | 避免只重复同一提示造成缓存偏差 |
| 鲁棒性 | 20 个基准，每个 3～5 个变体 | 固定随机种子，可复现 |
| 翻译 | 不少于 200 条 | 中英双向，覆盖通用、专业、长文、格式和噪声 |
| 报告写作 | 不少于 8 套材料包 | 每套带事实表、禁止项和 Rubric |
| 情报生产 | 不少于 8 套材料包 | 每套带实体、事件、时间线和来源映射 |

后续目标是在不降低参考答案质量的前提下，把翻译扩展到 400 条以上，报告和情报分别扩展到 15～20 套。素材数量不作为唯一目标，优先保证黄金答案和评分规则可审计。

### 6.3 EvalScope 标准 Benchmark 初始目录

首版目录建议从小而稳定的组合开始，最终启用项以阶段 0 的许可证和离线可用性核验为准：

| 能力 | 候选 Benchmark | 使用方式 |
| --- | --- | --- |
| 中文知识 | C-Eval、CMMLU、Chinese SimpleQA | 标准评测套餐，可选择子集和样本上限 |
| 通用知识/推理 | MMLU/MMLU-Pro、GSM8K、BBH | 与平台业务专项分开展示 |
| 指令遵循 | IFEval、Multi-IF | 与平台格式规则共同形成指令维度 |
| 真实性/幻觉 | TruthfulQA、HaluEval | 作为公共 Benchmark 参考，不替代业务黄金事实评分 |
| 长上下文 | Needle-in-a-Haystack、LongBench 系列 | 与平台定长 Token 用例共同分析 |
| 翻译 | WMT2024++ 的 `en-zh_cn` 等子集 | 标准翻译参考；平台另补中译英和业务规则 |
| 代码 | HumanEval、MBPP（可选） | 仅用户选择代码能力时安装和执行 |

EvalScope 的 WMT2024++ 当前覆盖英语到多目标语言，其中包括简体中文，并使用 BLEU、BERTScore 和 COMET；它不能替代平台规划的中译英、术语、格式、报告和情报翻译素材。

### 6.4 预置运行方案

| 方案 | 用途 | 默认范围 |
| --- | --- | --- |
| 快速体检 | 模型接入后快速发现明显问题 | 小样本能力、翻译、鲁棒和低并发，约 5～10 分钟 |
| 标准评测 | 日常版本验收和模型对比 | 全量基础测试、中等并发、部分进阶用例 |
| 深度评测 | 上线前正式验收 | 全量能力、长上下文、容量阶梯、突发、持续和全部进阶用例 |
| 自定义 | 指定测试集、参数和安全阈值 | 由用户配置并形成快照 |

时间只作为界面预估，不写入固定验收承诺；真实时长取决于模型规模、输出长度和硬件。

## 7. 用户测试素材

### 7.1 支持方式

- 在线新建和编辑单条测试用例。
- 复制内置测试集后修改。
- 导入 JSONL、CSV 和 ZIP 材料包。
- 报告/情报材料支持 TXT、Markdown、DOCX 和 PDF；导入时提取文本并保留原文件。
- 翻译支持双语对照表、术语表、专名表和翻译记忆素材。
- 草稿校验、预览、发布不可变版本、归档和复制新版本。

### 7.2 通用用例格式

```json
{
  "case_id": "translation-zh-en-001",
  "category": "translation",
  "name": "数字与机构名称保持",
  "language": "zh-CN",
  "messages": [{"role": "user", "content": "..."}],
  "references": ["..."],
  "rules": {
    "required_terms": [],
    "forbidden_terms": [],
    "protected_spans": [],
    "required_facts": [],
    "json_schema": null
  },
  "rubric": [],
  "tags": ["builtin", "translation", "entity"],
  "weight": 1.0
}
```

报告和情报材料的大文件只保存在 Artifact Store；数据库保存内容摘要、对象引用、哈希和索引字段。

### 7.3 导入安全

- 校验扩展名、MIME、文件签名、大小、数量和压缩展开比例。
- ZIP 解包必须阻止路径穿越和压缩炸弹。
- 不执行 DOCX 宏、PDF 脚本或测试素材中的任何代码。
- 提示词注入文本始终视为测试数据，不解释为平台控制指令。
- 上传完成先生成预览和校验报告，用户确认后才发布版本。

## 8. 评分体系

### 8.1 分层评分

1. **确定性规则评分**：JSON Schema、关键字段、数值、实体、术语、正则、长度、格式和禁止项。
2. **语义/裁判评分**：开放式答案的忠实度、完整性、逻辑性、流畅度和写作质量。
3. **人工复核**：正式验收、争议结果、裁判校准和抽样质检。

确定性规则始终保留明细，裁判模型不能覆盖明确的事实错误。例如数字被改写错误时，即使裁判认为文章流畅，也必须保留数字错误扣分。

### 8.2 裁判模型约束

- 默认选择独立于被测模型的本地裁判模型。
- 裁判输入隐藏被测模型显示名称，降低品牌偏差。
- 裁判结果保存 Rubric 子项、理由、置信度和裁判模型版本。
- 通过锚点用例定期检查裁判评分漂移。
- 敏感材料不得自动发送给外部裁判服务；只有项目授权且有审计记录时才允许。
- 无裁判模型时评测仍可完成，开放式维度显示“规则分 + 待人工复核”，不伪造完整总分。

### 8.3 结果展示原则

顶层不设置一个强制“万能总分”，而是并列展示：

- 能力质量总览。
- 翻译能力。
- 鲁棒性。
- 报告写作。
- 情报生产。
- 服务性能与容量。
- 稳定性与资源。

可以提供配置化综合参考分，但必须同时展示各维度原始指标和权重。不同测试集版本、不同模型参数或不同并发方案的运行默认不可直接排名；用户强制比较时显示明显的口径差异提示。

### 8.4 置信度

结果同时记录样本数、重复次数、标准差、失败样本和评分来源。样本不足、Token 仅为估算、裁判缺失或资源未绑定时，应降低置信度并在报告中明确说明。

## 9. 运行配置与不可变快照

提交运行时至少选择：

- 被测模型配置。
- 一个或多个已发布测试集版本。
- 快速、标准、深度或自定义方案。
- 温度、Top P、随机种子、最大输出长度和超时。
- 能力用例重复次数。
- 并发/RPS 阶梯、每阶段预热与测量时长。
- 可选裁判模型和人工复核比例。
- 可选服务器资产/活动会话绑定。
- 安全阈值和异常自动停止策略。

运行快照保存：

- 测试集版本 ID、内容哈希、用例 ID 列表和评分规则版本。
- 模型配置非敏感字段、模型参数和协议探测结果。
- 运行方案、并发参数、安全阈值和随机种子。
- 平台版本、评测引擎版本、开始时间和执行节点。
- 裁判模型非敏感版本信息。

快照不保存 API Key、鉴权头值、SSH 密码或其他凭据。

## 11. 运行状态机与任务执行

### 11.1 状态机

```text
draft（仅测试集）

queued -> preparing -> running -> scoring -> reporting -> completed
   │          │           │          │           │
   └──────────┴───────────┴──────────┴───────────┴──> failed
                          │
                          └── stop_requested -> stopped
```

运行阶段细分为能力、翻译、鲁棒、负载、评分和报告，使页面可以准确显示当前工作，而不是只显示一个百分比。

### 11.2 Worker 策略

- 第一阶段复用现有任务基础设施，新增 `ModelEvaluationManager` 和独立队列主题；EvalScope 在隔离子进程中运行，不加载进 Web 进程。
- 兼容性 PoC 后如果 EvalScope 依赖、运行时长或资源占用不适合同一 Worker，正式部署直接增加独立 Evaluation Worker 镜像；API、表结构和任务契约不变。
- 普通能力用例可在单次运行内部受控并发；评测运行之间默认串行或使用很小的全局并发，防止多个压测互相污染。
- 负载阶段对同一模型端点加分布式互斥或租约；同一端点默认只允许一个容量评测。
- Redis 失效时退化为数据库轮询，运行正文和状态不依赖 Redis。
- 后续评测量增加后，再把模型评测拆为独立 Evaluation Worker 进程，不改变 API 和数据库契约。

### 11.3 恢复与幂等

- 排队任务可安全重新领取。
- Worker 崩溃时，未完成的单用例依据唯一键避免重复写入；能力阶段可从未完成用例继续。
- 负载阶段发生中断时不拼接两个时间窗口，当前阶段标记无效并从阶段起点重跑。
- 评分和报告生成可基于已完成原始产物单独重试。
- 停止请求采用协作取消，停止发新请求并等待短暂清理窗口，不强杀平台或模型服务。

## 12. 模型调用、EvalScope 与观测实现

### 12.1 执行后端选择

- EvalScope 能直接表达的标准 Benchmark、WMT 和性能任务使用 `EvalScopeBackend`。
- 报告、情报、项目自定义规则和扰动成组逻辑首版使用 `NativeBusinessBackend`，成熟后可逐步封装为 EvalScope 自定义 Benchmark。
- 一个评测运行可以包含多个后端阶段，但平台只生成一个运行 ID、统一快照和统一报告。
- 结果映射器只读取 EvalScope 公开产物和稳定字段；原始 EvalScope 产物完整保留，无法识别的字段不得静默丢弃。

### 12.2 首版协议

优先支持 OpenAI 兼容 `/v1/chat/completions`。`EvaluationModelClient` 把不同服务返回统一为：

```text
request_id, started_at, first_token_at, completed_at,
http_status, finish_reason, input_tokens, output_tokens,
token_source, chunks, text, error_type, retry_count
```

流式请求以首个非空正文分片计算 TTFT，忽略只有角色或空文本的分片。请求、分片和完成时间使用单调时钟；墙钟只用于审计显示。

### 12.3 Token 计数优先级

1. 服务返回的 `usage`。
2. 与目标模型明确匹配、已在本地安装的 Tokenizer。
3. 保守估算，并明确标记 `estimated`。

平台不自动从互联网下载 Tokenizer，不启用来源不明的 `trust_remote_code`。如果模型服务不返回 usage 且没有匹配 Tokenizer，正式报告不得把估算 Token 当成精确计费或验收依据。

### 12.4 并发实现

标准性能任务复用 EvalScope `perf` 的固定并发、速率控制、开放环、预热和数据集插件；平台不再自研另一套底层 HTTP 压测器。`load_runner.py` 只负责把平台方案转换为 EvalScope 参数、执行安全预检、端点互斥、阶段停止和结果归一化。

原生业务后端仅用于低到中等并发的业务质量用例，不承担正式最大容量测量。后续如果 EvalScope 不能兼容某类私有协议，再通过其 Custom API 扩展或新增受测的原生适配器。

客户端本身的排队时间必须单独记录，不能把本地线程池排队误算为模型服务响应时延。

### 12.5 EvalScope 进度、停止与产物

- 适配器为每个阶段生成无密钥配置，并在受限环境变量中注入本次凭据。
- 子进程标准输出只提取白名单进度事件，完整诊断日志先脱敏再写入 Artifact Store。
- 停止时先发送协作终止并停止新请求，超时后只回收本次 EvalScope 子进程组，不操作模型服务。
- 阶段完成后校验退出码、报告文件、样本数和内容哈希，再映射为平台结果。
- EvalScope 异常、数据集缺失、可选指标模型缺失和许可证未确认分别归类，不统一显示成“模型调用失败”。

## 13. 负载安全护栏

### 13.1 提交前检查

- 只允许使用模型配置中心中已授权的目标，不允许普通用户通过评测接口临时输入任意 URL，降低 SSRF 风险。
- 连通性、流式兼容、上下文限制和小流量预热通过后，才能进入容量阶段。
- 展示目标模型、目标服务器、并发阶梯、预计请求量和预计时长。
- 深度或自定义高负载方案要求具备 `evaluation:operate` 权限，并记录审计。

### 13.2 自动停止条件

默认对滚动窗口监测：

- 错误率或超时率持续超过阈值。
- P99 持续超过请求超时上限。
- 连续连接失败或服务不可用。
- 用户配置的 GPU 温度、显存、CPU 温度或系统内存阈值被触发。
- 用户主动停止。

安全阈值必须写入运行快照。触发后停止发新请求、保存已完成样本、标记触发原因并生成不完整运行报告。平台不会自动重启模型服务或终止业务容器。

### 13.3 负载隔离

- 容量结果只在没有其他已知评测占用同一端点时有效。
- 关联服务器时记录测试前、中、后的资源基线。
- 报告标明是否存在无法观测的外部流量；无法确认独占时把容量结论标记为“共享环境参考值”。

## 14. API 设计

统一前缀建议为 `/api/model-evaluation`。

### 14.1 测试集

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/suites` | 查询内置和当前项目测试集 |
| POST | `/suites` | 新建项目测试集草稿 |
| POST | `/suites/{id}/clone` | 复制内置或现有测试集 |
| POST | `/suites/{id}/import` | 导入用户素材并校验 |
| POST | `/suites/{id}/versions` | 发布不可变版本 |
| GET | `/suites/{id}/versions/{version}` | 查看版本清单和用例摘要 |
| POST | `/suites/{id}/validate` | 预检用例、引用和评分规则 |

### 14.2 运行与结果

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/runs` | 提交评测，返回 `202 queued` |
| GET | `/runs` | 当前项目运行列表和筛选 |
| GET | `/runs/{id}` | 运行详情、阶段和摘要 |
| GET | `/runs/{id}/events` | 增量事件和进度 |
| POST | `/runs/{id}/stop` | 停止排队或运行中的评测 |
| GET | `/runs/{id}/results` | 分页查询用例结果 |
| POST | `/runs/{id}/rescore` | 使用新裁判或人工规则重新评分，不重跑模型 |

| POST | `/comparisons` | 创建同口径模型/版本对比 |

所有写接口继续使用 CSRF 防护和项目权限校验。越权访问按平台现有约定返回不可枚举的结果。

## 15. RBAC 与审计

新增项目级权限：

| 权限 | 能力 |
| --- | --- |
| `evaluation:view` | 查看当前项目测试集、运行、结果和报告 |
| `evaluation:manage` | 创建、导入、编辑、发布项目测试集和人工复核 |
| `evaluation:operate` | 发起、停止、重评分和执行负载测试 |

模型配置和密钥仍由平台级模型管理权限控制。具备评测执行权限的项目用户可以选择已授权的模型配置执行，但无法读取密钥。

审计至少记录：测试集创建/发布/归档、素材导入、运行提交/停止、裁判变更、人工评分、报告下载和高负载参数。审计内容不记录完整提示词、响应正文和凭据。

## 16. 前端信息架构

侧栏在“测试工作台”增加“模型评测”，不塞入现有“模型配置”页面。页面包含：

1. **评测总览**：最近运行、模型能力雷达、容量摘要、风险和待复核项。
2. **新建评测**：模型、测试集、运行方案、裁判、服务器绑定和安全阈值。
3. **运行监控**：阶段进度、实时吞吐、P95/P99、错误率、并发、Token 和资源曲线。
4. **测试集管理**：内置库、项目库、复制、导入、校验、版本和用例预览。
5. **结果与报告**：维度得分、失败用例、翻译/报告/情报明细、人工复核和下载。
6. **模型对比**：仅默认展示同测试集版本、同参数的运行；不同口径需要显式确认。

页面面向普通测试人员显示业务名称和解释性结论，内部 ID、原始 JSON 和诊断字段放在详情区。

## 17. 报告设计

模型评测报告至少包含：

1. 执行摘要与是否达到验收阈值。
2. 被测模型、推理引擎、量化和硬件环境说明。
3. 测试集版本、样本量、参数和评分方法。
4. 能力质量、翻译、鲁棒、报告写作和情报生产结果。
5. TTFT、TPOT、吞吐、并发、容量拐点和错误分布。
6. CPU/GPU/内存资源曲线及采集可用性。
7. 失败用例分类、典型问题和风险说明。
8. 裁判模型、人工复核比例和结果置信度。
9. 同口径历史或模型对比。
10. 结论、上线建议和限制条件。

报告明确区分“事实测量”“规则评分”“裁判意见”和“人工结论”，不得把估算 Token、缺失资源指标或低样本结果包装成确定结论。

## 18. 配置建议

平台配置只保存全局安全上限和功能开关，不保存公司服务器或明文凭据。建议配置项包括：

```yaml
model_evaluation:
  enabled: true
  execution_mode: embedded
  default_backend: evalscope
  evalscope_runtime: isolated_process
  evalscope_version: locked
  dataset_network_access: false
  max_active_runs: 1
  max_case_concurrency: 8
  max_load_concurrency: 64
  max_run_duration_seconds: 14400
  raw_response_retention_days: 30
  allow_external_judge: false
```

以上为建议结构，不在方案阶段直接写入生产配置。`locked` 表示由兼容性测试确定并锁定准确版本/提交和离线依赖清单，不允许生产环境跟随 `main` 自动升级。PyCharm 本地模式继续可使用 `embedded`，正式环境随现有部署使用 `external` Worker。不会自动占用新的 Web 端口。

## 19. 开发分期

排期基线为 **4 个工作日**，四个技术阶段各占一个工作日。压缩排期不删减隔离运行、离线资源、协作停止、权限安全、凭据保护和自动化回归；每个工作日均按“实现、定向测试、文档与计划同步、当日验收”形成闭环。真实模型、额外 GPU 或维护窗口属于外部验收资源，未及时提供时标记为待实机复验，不阻塞可由 Mock 和隔离环境完成的代码交付。

### 工作日 1 / 阶段 0：基础契约与可测试骨架

完成状态：**已完成（2026-09-01）**。兼容性证据、复现命令和已知边界见 `docs/evalscope-compatibility-poc.md`。

- 完成 EvalScope 固定版本兼容性 PoC：Python 3.11、OpenAI 兼容 API、Mock、标准评测、`perf`、WMT、结果解析、停止和离线数据。
- 建立 `EvaluationBackend`、`EvalScopeBackend`、结果映射器和隔离进程运行器，输出依赖清单及许可证清单。
- 数据表、Store 契约、领域对象、内置清单加载和项目权限。
- Mock 模型服务与确定性假数据，不依赖真实模型即可回归。
- 运行状态机、外部 Worker 领取、停止和恢复。

当日验收出口：固定版本候选、依赖与许可证清单明确；Mock 模型可完成隔离运行、停止和结果映射；运行骨架、数据契约和权限回归通过。

### 工作日 2 / 阶段 1：基础评测 MVP

当日验收出口：用户可从烈马平台提交、观察、停止并查看至少一个标准能力评测和一组 `perf` 结果，Token 来源、错误分类和项目隔离清晰可追溯。

## 20. 测试策略

### 20.1 自动化测试

- 模型协议：流式、非流式、空分片、usage 缺失、错误状态、超时和取消。
- EvalScope 适配：固定版本契约、参数映射、子进程停止、退出码、进度脱敏、结果映射和未知字段保留。
- EvalScope 数据：在线预取、许可证门禁、内容哈希、本地强制加载和断网运行。
- Token：三种来源、截断、估算标识和长度遵循。
- 数据集：内置清单哈希、版本不可变、项目隔离、导入校验和恶意 ZIP。
- 运行：领取、幂等、停止、Worker 重启、Redis 降级和阶段恢复。
- 性能：固定时钟/假服务验证 TTFT、吞吐、百分位和本地排队口径。
- 鲁棒：固定种子、基准不足时 N/A、平均值和最差值。
- 翻译：数字、实体、术语、格式、保护片段和多参考答案。
- 评分：规则不可被裁判覆盖、裁判缺失降级、人工复核审计。
- 安全：凭据不出现在 API、日志、快照、产物和报告中。
- RBAC：跨项目列表、详情、产物下载、运行和高负载操作。
- 报告：DOCX/PDF 结构、图表、中文字体和敏感字段检查。

### 20.2 验收环境

1. Mock 模型：开发期稳定复现正常、慢响应、截断、错误和过载。
2. 用户提供模型：验证协议、Token、流式、并发和真实结果。
3. 脱敏业务材料：验证报告和情报生产的实际适用性。
4. 维护窗口：执行深度负载和容量评测，避免影响线上业务。

## 21. 首版验收标准

- 内置测试集可见、只读、可复制，版本内容和哈希不可变。
- EvalScope 版本、Benchmark 名称、数据集 ID/版本/许可证和内容哈希进入运行快照；正式运行不临时联网下载。
- 至少一个标准能力 Benchmark 和一组 `perf` 任务可经 EvalScope 隔离运行并映射为平台统一结果。
- 用户可在当前项目创建测试集、导入素材、校验并发布版本。
- 至少一个 OpenAI 兼容私有模型可完成流式与非流式评测。
- Token 来源被准确标记，估算值不冒充精确值。
- 基础能力、翻译、鲁棒和并发评测可以排队、停止、恢复并持久化。
- 页面实时展示进度、TTFT、吞吐、P95/P99、成功率和错误分类。
- 同一模型端点不会同时运行两个容量测试。
- 自动停止条件触发后不再发新请求，已完成数据和原因可追溯。
- 报告写作和情报测试能展示规则评分、裁判/人工状态和典型错误。
- 可生成结构完整的 DOCX/PDF 报告及 JSONL/CSV 明细。
- 模型密钥、SSH 密码和用户素材不会跨项目或进入非授权响应。
- 新增自动化测试通过，现有业务自动化、接口、服务器性能和报告能力无回归。

## 24. EvalScope 版本、许可证与离线策略

- 参考项目：[ModelScope EvalScope](https://github.com/modelscope/evalscope)。截至 2026-09-01，其 GitHub 最新发布为 V1.11.1；开发不得直接依赖浮动 `main`，也不得仅因版本最新便直接进入生产，需要在工作日 1 兼容性验收后锁定准确版本或提交。
- EvalScope 项目代码使用 Apache-2.0 许可证。发布镜像和交付包时保留相应 LICENSE/NOTICE 与第三方依赖清单。
- EvalScope 支持的各数据集具有独立许可证和使用条件，不能因为框架是 Apache-2.0 就默认可以复制或商用分发。
- 标准数据集由管理员在受控有网环境预取，记录来源、版本、许可证、文件清单和 SHA-256，再导入正式环境；正式 Worker 默认禁止访问数据集公网源。
- COMET、BERTScore、Tokenizer 等附加模型也按数据资产管理，必须预下载、锁版本、核许可证和哈希，不在评测运行中临时下载。
- EvalScope 升级需要重新执行协议、指标、结果映射、数据集哈希、离线构建和基准回归；旧运行继续保留原执行版本，不能用新版本静默重算后覆盖。

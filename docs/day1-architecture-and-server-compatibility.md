# 第 1 工作日：架构审计与服务器兼容性落地

## 今日结论

当前项目已经具备完整的单机版骨架，不适合推倒重写。正确路线是保留烈马自动化测试流水线和现有页面，在边界处逐步替换存储、任务执行和身份认证。

今天优先补齐了服务器压测最缺失的前置能力：只读兼容性探测。平台现在能够先判断目标服务器是否可执行、是否需要降级、或者必须阻断并输出前置条件，再决定是否启动压测。

## 当前架构审计

| 领域 | 当前实现 | 主要限制 | 改造方向 |
| --- | --- | --- | --- |
| Web/API | FastAPI 单进程，静态前端 | API 与执行生命周期在同一进程 | 保留 API 契约，逐步把执行交给独立 Worker |
| 自动化任务 | `TaskManager` + 单后台线程 | 只能单实例，Web 重启影响任务 | 抽象 TaskQueue，先兼容本地队列，再接 Redis |
| 压测任务 | 每个任务创建守护线程 | 无全局并发治理，进程退出即中断 | 独立 Server Worker，增加租约、心跳、取消和并发上限 |
| 报告任务 | 独立后台线程 + SQLite 状态 | 仍依赖 Web 进程 | 复用统一任务状态机和 Worker |
| 元数据 | `tasks.db`、`platform.db` 两个 SQLite | 多实例写入与多人隔离能力有限 | 定义 Repository 接口，迁移到 MySQL；SQLite 保留开发模式 |
| 文件资产 | 本地 `runtime/`、`artifacts/` | 多实例不可共享，生命周期分散 | 定义 ArtifactStore，生产接 MinIO，本地目录保留开发实现 |
| 身份权限 | 单个 Web API Key | 无用户、项目隔离、RBAC、审计主体 | 增加用户、项目、角色、权限、审计日志和凭据密文存储 |
| 服务器接入 | Paramiko + 密码，可自动信任主机 | 缺少主机指纹治理；页面密码曾进入任务参数 | 密码不落库；下一步接凭据引用、known_hosts 和密钥认证 |
| 服务器兼容性 | 压测时边运行边发现缺工具 | 会现场安装/编译，失败结论不清晰 | 先只读预检，再选择已有工具、离线工具或 Python 降级 |

## 今日实现的兼容性策略

1. 检查 OS、版本、内核、CPU 架构、用户与 root 权限。
2. 检查包管理器和 Docker/Podman/nerdctl，但不自动安装或修改它们。
3. CPU 优先使用已有 `stress-ng`，缺失时使用 Python 3 降级；两者都没有则阻断。
4. GPU 监控以 `nvidia-smi` 为基线；GPU 压测以已有或可构建的 `gpu-burn` 为执行器。
5. `DCGM` 仅标记为可选诊断/指标增强，不作为 GPU 压测前置条件。
6. `nccl-tests` 仅用于后续多卡通信测试，不与单卡压力测试混为一体。
7. 驱动、CUDA、容器运行时和内核由运维预装；平台只检查、选择执行器、降级或输出缺失清单。
8. openEuler、Ubuntu LTS 作为主支持系统；CentOS 作为存量兼容维护系统。

## 目标架构与实施顺序

### 第一阶段：先抽象边界，保持单体可运行

- `TaskRepository`：替代业务代码直接依赖 SQLite。
- `TaskQueue`：替代 Web 进程内线程调度。
- `ArtifactStore`：替代业务代码直接拼接本地文件路径。
- `SecretProvider`：任务只保存凭据引用，不保存 SSH/模型明文。
- `ServerCapabilityProbe`：所有服务器测试统一经过预检。

### 第二阶段：接入企业基础设施

- MySQL 保存用户、项目、任务、接口版本、报告元数据与审计日志。
- Redis 保存队列、Worker 心跳、短期状态和实时消息，不作为最终事实库。
- MinIO 保存上传快照、日志、图表、报告和压测产物，数据库只保存对象键和校验值。
- Web、Automation Worker、Server Worker、Report Worker 分进程部署。

### 第三阶段：多人协作和安全治理

- 用户属于项目，任务和资产强制带 `project_id`。
- RBAC 至少包含管理员、项目负责人、测试人员、只读访客。
- SSH/模型凭据密文保存，API 永不返回明文。
- 高风险操作、凭据使用、任务启动/停止、报告下载进入审计日志。

## 明日建议

1. 给 SQLite Store 定义最小 Repository 协议，先不接 MySQL，保证迁移有明确边界。
2. 给本地资产目录定义 ArtifactStore 接口，避免后续 MinIO 改造遍布业务代码。
3. 增加压测任务并发上限、排队和安全阈值；目前一个请求对应一个线程，不适合多人使用。
4. 用真实的 openEuler、Ubuntu、CentOS 和 NVIDIA GPU 服务器跑能力探测，形成第一版兼容矩阵。

## 需要协助的资源

进入真实兼容验证时，需要以下测试资源；今天的本地实现和单元测试不依赖这些资源：

- 一台 openEuler 服务器、一台 Ubuntu LTS 服务器；CentOS 仅在确有存量环境时提供。
- 至少一台 NVIDIA GPU 服务器，普通账号和 root/运维账号各一套，用于验证权限差异。
- 一份经确认可用于项目分发的 gpu-burn 源码包或预编译二进制；当前代码不再依赖个人电脑路径。
- 如果需要多卡通信验证，再提供安装好的 `nccl-tests` 或其离线包。
- 如需 DCGM 诊断验证，可提供已安装 DCGM 的机器；它不是压测必需资源。
